# SDITT Project Memory

## Context

This project contains the MATLAB implementation of SDITT from Chen Jiayin's doctoral dissertation:

`陈嘉胤博士论文-231019-高速铁路道岔区轮轨多体系统耦合动力学建模及仿真分析.pdf`

SDITT means `Simulation for Dynamic Interaction of Track Turnouts`. It is a high-speed vehicle-turnout rigid-flexible coupled dynamics simulation program. The model focuses on wheel-load transition, wheel-rail multi-point contact, wheel-rail impact, and medium/high-frequency vibration in railway turnout zones, with analysis frequency up to about 2000 Hz.

The MATLAB code is mainly under:

`SDITT-RW-FT-250728/`

All Python code for this project should live under:

`python/`

Use `python/` for existing and future `.py` files, including generated scripts,
modules, packages, and Python migration work, unless the user explicitly asks
for a different location.

The current main script appears to be:

`SDITT-RW-FT-250728/SDITT_CR400_NoStrTIrr_250728_Face.m`

## Core Model Understanding

SDITT is not a simple vehicle-track coupling model. It is a tightly coupled time-domain simulation made of these main modules:

1. Vehicle multi-body dynamics
   - Vehicle contains carbody, bogies, wheelsets, primary and secondary suspension.
   - Each rigid body considers lateral displacement, vertical displacement, roll, pitch, and yaw.
   - Suspension force elements include nonlinear dampers and spring-damper series elements.
   - Current main script defaults to `CRH380A_v6`.
   - Current main script defaults to rigid wheelsets with `InpPar.NM_FW = 0`, while flexible wheelset support still exists.

2. Flexible turnout dynamics
   - Turnout model uses finite element modal superposition.
   - It considers variable-section rails, shared baseplates/sliding plates, turnout slab, base slab, interlayer constraints, adjacent rail constraints, spacer irons, bolts, and locking/support constraints.
   - Current main script defaults to `InpPar.Type_Track = 'FT-Modal'`.
   - Modal cutoff frequency is set to `CutFreq_FT = 2000`.
   - Modal matrices are generated by `Matrix_Modal_FT_230313.m`.

3. Wheel-rail multi-point contact geometry
   - Turnout contact is multi-rail and multi-patch.
   - Current code uses dummy rail/contact patch labels such as `L1`, `R1`, `R2`, `R3`.
   - Contact geometry combines wheel profile, rail profile, wheelset pose, rail dynamic displacement, and track irregularity.
   - A quasi-elastic correction is used to avoid contact point jumping and abnormal numerical impact.
   - Main contact controller: `Multi_Con_250812.m`.

4. Normal contact
   - Thesis recommends STRIPES semi-Hertz normal contact for non-Hertzian turnout rail contact.
   - Current main script selects:
     - `InpPar.Type_Normal = 'STRIPES&ConDamp'`
     - `InpPar.ConDamp = 'Hu-Guo'`
     - `InpPar.ConDamp_Coff = 0.83`
   - STRIPES implementation: `NF_STRIPES_230623.m`.
   - Hu-Guo normal contact damping is used to represent wheel-rail impact energy dissipation.

5. Tangential contact and creepage
   - Thesis describes Kalker simplified theory / FASTSIM.
   - `FASTSIM.m` exists.
   - In current `Multi_Con_250812.m`, the FASTSIM call is preserved but commented. The active path calculates Kalker linear creep coefficients and then applies nonlinear saturation correction.
   - Creepage calculation is especially important in turnout zones because rail lateral bending and contact point migration strongly affect lateral creepage.

6. Time integration
   - The thesis develops a variable-step implicit Park integration algorithm.
   - Current code uses `InpPar.Int_Method = 'Park'`.
   - Candidate time steps are generated as `Range_drtaT = 1e-4 ./ (2.^(0:1:12))`.
   - Integration uses wheel-rail normal force error and combined normal/tangential force error as convergence criteria.
   - Integration implementation: `Integration_Park.m`.

## Main MATLAB Execution Flow

The main script loops over two stages:

1. `Preload`
   - Pre-balances the vehicle-track/turnout system before the formal simulation.

2. `Cal`
   - Loads the preload state and performs the actual simulation.

High-level flow:

1. Set paths, turnout type, vehicle type, contact model, integration method, speed, and direction.
2. Load or build track/turnout matrices.
3. Build vehicle mass, stiffness, and damping matrices.
4. Assemble global system matrices `Mxt`, `Kxt`, and `Cxt`.
5. Build gravity load vector.
6. Initialize time integration states and output structs.
7. Load/generate rail and wheel profiles.
8. March by mileage/time.
9. For each time step, search a converged integration time step.
10. Inside each implicit iteration:
    - Update nonlinear vehicle damping.
    - Add gravity and curve-related external forces.
    - Map wheel-rail forces to vehicle subsystem.
    - Map wheel-rail forces to track subsystem.
    - Integrate displacement/velocity/acceleration using Park/Newmark/Houbolt path.
    - Recover rail displacement, velocity, and acceleration.
    - Reconstruct wheel-rail contact geometry.
    - Compute normal contact, damping, creepage, and tangential forces.
    - Check force convergence.
11. Store dynamic/contact results in `ZP_Dyn`, `ZP_Con`, `ZP_Dis`, `ZP_Vel`, `ZP_Acc`, etc.

## Python Migration Notes

Do not mechanically translate MATLAB files one by one. A better Python architecture should split the current monolithic flow into clear modules:

- `config` / `parameters`
- `profiles`
- `vehicle`
- `track_modal`
- `contact_geometry`
- `normal_contact`
- `tangential_contact`
- `integrators`
- `simulation_loop`
- `outputs`

The most difficult migration target is `Multi_Con_250812.m`, because it currently mixes:

- wheel and rail profile interpolation,
- track irregularity interpolation,
- flexible wheelset handling,
- contact geometry screening,
- quasi-elastic correction,
- normal contact,
- normal contact damping,
- creepage calculation,
- tangential force calculation,
- coordinate transforms,
- force aggregation,
- output struct packing.

This file should be decomposed before translating.

### Vehicle Parameter And Matrix Port

Python now includes the CRH380A rigid-wheelset vehicle parameter/matrix path
corresponding to:

- MATLAB parameters: `SDITT-RW-FT-250728/Par_Vehicle_CRH380A_v6.m`
- MATLAB matrices: `SDITT-RW-FT-250728/Matrix_Vehicle_RW_230409.m`
- Python parameter reader: `python/sditt/vehicle/parameters.py`
- Python matrix builder: `python/sditt/vehicle/matrices.py`

Use:

```python
from sditt.config import ProjectPaths
from sditt.vehicle import build_vehicle_matrices_rw_230409, load_vehicle_parameters

paths = ProjectPaths.from_repo_root()
vehicle = load_vehicle_parameters(paths.default_vehicle_parameters)
matrices = build_vehicle_matrices_rw_230409(vehicle)

M_vehicle = matrices.M_vehicle
K_vehicle = matrices.K_vehicle
C_vehicle = matrices.C_vehicle
```

The Python builder keeps the original MATLAB 1-based DOF assembly formulae at
the call sites and translates indices only in small helper functions. This is
intentional: it makes later MATLAB/Python diffing easier and reduces migration
indexing mistakes.

Current output shape is `51 x 51` for `M_vehicle`, `K_vehicle`, and
`C_vehicle`. `VehicleMatrices` also exposes MATLAB-compatible aliases:
`Mlc`, `Klc`, `Clc`, and `Clc_0`.

The parameter reader now applies the MATLAB lateral-stop table post-processing
for `K_STy_Table` (`mirror + sortrows`) and should report no unsupported
statements for `Par_Vehicle_CRH380A_v6.m`.

## Key Thesis Takeaways for SDITT

- Traditional turnout dynamics models are often valid only below about 20-100 Hz; SDITT targets up to about 2000 Hz.
- Turnout wheel-load transition can excite medium/high-frequency wheel-rail impact, especially near switch and crossing regions.
- Flexible turnout modeling is important because rigid/lumped turnout models may fail to represent impact decay and high-frequency rail response.
- Wheelset flexibility affects wheel-rail impact velocity, normal contact damping, axlebox acceleration, and modal response.
- Turnout structural irregularity, especially lateral bending of stock/wing rails and top-width transition of switch/point rails, strongly affects creepage and lateral wheel-rail force.
- STRIPES + Hu-Guo damping is selected for normal contact because it better represents non-Hertz contact and impact energy dissipation.
- Variable-step Park integration improves efficiency while maintaining force convergence, with thesis reporting nearly 4x efficiency improvement compared with small fixed-step integration.
